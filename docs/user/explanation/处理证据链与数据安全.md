# 处理证据链与数据安全

理解 MyGPR 为什么"每一步都可回溯、任何中断都不丢数据"。操作步骤见[任务指南](../how-to/index.md)。

## 处理证据链

每次处理（单步或流水线）都产出一份**处理清单（manifest）**，回答四个问题：

1. **输入是什么** —— 输入数据的 SHA-256、来源成果 ID、数据集元数据
2. **做了什么** —— 算法 ID 与版本（`implementation_version`，如 `native-1.0`）、参数（用户参数与运行时参数分开记录）、执行轴（分块/全局）
3. **输出是什么** —— 输出 SHA-256、形状、有限性摘要
4. **何时何人** —— 时间戳、耗时、运行时警告

关键设计：

- **算法单一事实来源**：全部 36 个方法由 `NATIVE_ALGORITHMS` 注册表驱动，GUI、CLI、AutoTune、证据导出走同一实现——不存在"界面一个结果、脚本一个结果"。
- **等价性验证**：每个算法都有数值等价证据（与历史参考核的逐位/容差对比，或被摘要钉死的 golden 数据），由测试矩阵持续保证。营山六测线真实数据的全文件哈希回归即其中一环。
- **不可变性**：处理清单为 `immutable-evidence` 治理域——只追加、不修改；处理成果按分支树组织，不覆盖旧结果。

对交付的意义：报告包里的每个数字都能沿证据链回溯到原始采集数据的精确字节。

## 数据安全模型

### 原子性

所有文件写入走"临时文件 → fsync → 原子重命名"。观察者永远看到旧版本或新版本，不会看到写了一半的文件。

### 事务与恢复

结构性修改（导入、保存成果）使用事务日志：

- **进程崩溃 / 断电**：重新打开项目时自动回滚未完成事务（文件与数据库目录一致）。
- **磁盘写满（ENOSPC）**：写入失败触发整体回滚——导入不留半成品测线，原始数据容器保持字节级不变（有注入测试钉住此契约）。
- **取消**：长任务随时取消，已产生的临时内容清除。

### 备份的完整性

备份压缩包含 SHA-256 清单，**创建后立即执行恢复式校验**。增量备份记录基准链与逐文件哈希，恢复时合并并逐成员校验——坏档在恢复时报错，而不是交出损坏数据。

### 并发保护

项目目录带进程锁（含宿主与进程启动标记）：第二个进程以写模式打开会提示或只读降级，防止双写损坏。

## 什么时候你会感受到这些

- 导入中途拔电源：重新打开项目，没有那条测线，也没有残留目录。
- 处理到 99% 断电：成果目录没有半成品；重跑即可。
- 磁盘满导致失败：报错信息明确；原始数据完好。
- 交付后客户质疑某图：沿报告包的证据链与 SHA-256 清单可逐级复核到原始数据。
